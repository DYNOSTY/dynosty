## 온돌 둥지 자유 배치·고정 잠자리 v13 (현재 로컬 구현)

C1 조작: 지을 건물을 선택하면 완성 모습이 커서를 따른다. ←→키로 회전한 뒤 원하는 위치·방향으로 클릭한다. 필요한 자원을 보유했을 때 가까운 유휴 주민이 자재를 운반해 건설한다. 완공된 둥지에는 거주지가 없는 주민을 배정하고, 빈 잠자리는 이후 합류할 주민을 위해 남긴다. 주민의 잠자리는 고정한다.

이번 단계에서는 온돌 둥지에 이 조작을 먼저 적용했다. 제재소·광산·식당 등은 기존 고정 부지 건설을 유지한다.

- ‘온돌 둥지 증설 · 목재20’을 누르고 지도 위로 커서를 옮기면 기존 한국식 온돌 둥지의 완성 모델이 반투명하게 따라온다. ←→로15°씩 회전하고, 클릭으로 확정하며 Esc/취소 버튼으로 취소한다. 회전 중 카메라 방향키 조작은 막는다. 마우스로 카메라를 회전·이동하는 것은 가능하며 드래그가 건설 클릭으로 처리되지 않는다.
- 정해진 주거 구역이나 지정 부지 제한은 없다. 건물 바닥 전체가 평평하고 비어 있는 자리면 허용한다. 지도 밖, 건물/시설/작업 공간·주민·남아 있는 숲·광맥 겹침, 경사, 이웃 출입구를 막는 배치는 거부한다. 초록/빨강 테두리와 이유를 표시하며, 서버 계산 역할의 Worker에서 클릭 순간 다시 검사한다.
- 개발 수치: 커서 위치0.25 간격, 회전15°, 바닥 높이 차 허용0.12, 목재20, 공사8분(자재 운반 제외), 건강한 유휴 건설 인력 최대3명. 완만한 경사를 자동으로 깎아 건설하지 않는다. 높이가 있는 평탄한 곳과 고갈되어 평탄해진 숲도 허용한다.
- 주문 시 목재20을 공동 재고에서 확보하고 같은 금액을 다시 차감하지 않는다. 건설 인력은 작업장/기존 임무/식사 중인 주민을 빼앗지 않고 가까운 순서로 자동 선발한다. 작업 공간이 좁으면 접근 가능한 공사 위치에 맞춰1~3명으로 구성한다.
- 인력은 공동 자재 야적장에 가서 총20을 나눠 들고 현장으로 운반한다. 자재가 전부 도착하고 실제 현장 인력이 있어야 공사 시간이 흐른다. 자재 수량·운반 단계·교대·공사 시각을 저장한다. 질병/사망 시 물량을 보존해 유휴 인력이 인계하며, 교대자가 아직 이동 중이면 현장 작업자로 세지 않는다. 임의 질병/사망 확률은 추가하지 않았다.
- 완공 시 선택한 위치·방향으로 실제 건물을 만들고, 회전한 출입구와 건물을 반영해 귀가·우회 동선을 계산한다. 건설자는 배치를 해제하고 기존 식사·귀가·다음 임무로 돌아간다.
- 각 주민에게 둥지와 고정 잠자리 시작 번호를 배정한다. 기존 주민의 잠자리부터 보존하고 남은 자리에 신규 주민을 배정한다. 종별 공간2/1/2 기준을 유지한다. 거주자가 없는 둥지도 철거/재배정 없이 남아 이후 합류 시 사용한다. ‘입주 현황’에서 주민별 고정 잠자리를 확인한다. 실내를 별도로 그려 잠자는 애니메이션을 표시하는 단계는 아니다.

저장v13: v10/v11/v12에서 기존 입주와 진행을 보존하고 잠자리를 부여한다. 기존 저장 원본을 덮어쓰지 않고 `dynosty.timber.saves.v13`에 별도 기록한다. 위치·방향·자재 합계20·건설 인력 중복/다른 업무 충돌·잠자리 중복·정원·귀가 위치를 검사한다. 이전 버전의 진행 중 공사는 기존 방식으로 이어가고 새 둥지부터 자재 운반 건설을 적용한다.

검증: 기본 검사221개(28파일), 조달·생활 브라우저21개와 기존 카메라1개 확인. 완성 모델 커서 이동·잘못된 자리 거부·←→ 회전·Esc 취소·확정·자재 운반·완공·거주 부족 해소·저장 복원을 실제 브라우저에서 검사했다. 빈 둥지 선건설 후 합류와 기존 잠자리 보존, 운반 중 질병 교대와 현장 도착 전 완공 방지, v12 변환은 Core 검사에 포함한다. 커밋·푸시·PR·병합 없음.

남은 범위: 다른 시설의 자유 배치/회전, 실내 침상·수면 아트와 애니메이션, 재료별 건설 단가/건설 속도 밸런스, 건설 취소·환불·철거·건물 이전, 대규모 실시간 성능과 서버 DB 동기화. 현재 둥지 수 한도100곳은 개발 한도로 유지한다.

## 광산·채석장과 확대 지도 v12 (이전 구현, v13 둥지 배치 추가)

- 개발 지도512×512, 좌표±252. 기존 마을·시설 좌표는 유지한다. 둘레 숲4곳을 추가해 숲13곳이며 기존 숲9곳의 자원과 진행은 보존한다. 새 숲 위치는 거주지 북서·북동·남서·동쪽이다.
- 석탄광2곳(서부/동부 함지), 철광산2곳(북부/남부 함지), 채석장2곳(서부/동부 암반). 광산 지형은 주변보다 낮은 함지이며 광맥·입구·작업장·저장소·운반 수레를 표시한다. 채석장은 암반 노출과 낮은 채취 지형으로 구분한다.
- ‘작업장 권역’을 고르고 작업장과 저장소를 건설한다. ‘작업 인원’0~4명을 정하면 자동 출근·채취·운반한다. ‘채굴 현장 보기’로 선택한 광산이나 채석장에 카메라를 옮긴다. 숲 권역에서는 기존 제재소와 ‘벌목 현장 보기’를 유지한다.
- 석탄광→석탄, 철광산→철광석, 채석장→석재. 철광석은 철재와 별도의 제련 전 원료다. 현재 제련소·철광석→철재 전환과 석재 건설 비용은 구현하지 않았다. 채굴만으로 철재가 늘지는 않는다.
- 자원은 현장→수레→저장소 하역 후에만 공동 재고로 들어간다. 자원지별 잔량·배치·진행·수레·입고를 보존하고 같은 자원의 여러 광산은 한 공동 재고에 합친다. 기존 목재·철재 계약 장부와 새 광물 장부를 함께 검증한다.
- 숲 고갈만 나무 제거·평탄화·지정 주거 부지 개방으로 이어진다. 광맥 고갈 시 채취는 중단하지만 함지와 채석장 흔적은 유지한다. 이를 자동 주거 부지로 전환하지 않는다.

개발 수치: 시설별 목재20·건설8분(이동 별도), 인원 최대4, 실제 근무10분/인당 자원1, 현장 적재20·수레5. 석탄광별180, 철광산별160, 채석장별240. 현재는 목재와 동일한 자동 배치·출근·교대·운반 흐름을 공통으로 사용하며 자원별 장비·작업 속도·제련 효율·위험률은 아직 추가하지 않았다. 임의 질병·사망 확률도 넣지 않는다.

저장v12: 기존v10/v11 기록의 숲·주민·시설·계약·재고를 보존하고 새 둘레 숲4곳과 광물6곳을 추가한다(v10은 기존 추가 숲도 초기화). 이전 저장에서 없던 철광석·석재는0으로 시작한다. v12는 `dynosty.timber.saves.v12`에 별도로 기록하며 v10/v11 원본은 덮어쓰지 않는다. 잘못된 권역·좌표·중복 인력·자원 장부 불일치는 거부한다.

## 분산 숲·권역별 제재소 v11 (이전 구현, v12 광물 생산으로 확장)

C1 설정: 숲은 복홀 중앙·외곽·구석에 퍼져 있고, 전체 단계의 플레이를 거치며 목재 확보와 건설 부지 확장을 함께 이끈다. 개별 주민에게 벌목을 지시하지 않고 권역의 제재소에 인원수만 배치한다.

- 숲9곳: 서쪽, 중앙 동쪽, 북쪽, 동쪽, 남쪽, 북서·북동·남서·남동 구석. 개발용으로 권역마다 목재120을 두며 자원·생산 진행·현장 적재·제재소·저장소·배치·수레·누적 입고를 각각 관리한다.
- ‘제재소 권역’을 선택해 해당 숲 근처 지정 부지에 제재소와 저장소를 건설한다. 인원0~4명을 정하면 자동 고용·출근하고, 해당 권역의 숲만 줄인다. 이전 제재소와 저장소는 유지되며 여러 권역이 동시에 운영된다.
- 작업장 인력과 운반 인력은 서로 빼앗지 않는다. 각 권역의 수레가 하역한 목재는 한 공동 재고에 합친다. 계약으로 들어온 목재와도 같은 장부를 사용한다. 질병·사망·인력 부족 교대 및 빈 수레 복귀·정리는 권역별로 기존 규칙을 재사용한다.
- 한 숲이 고갈되어도 다른 숲은 줄거나 평탄해지지 않는다. 고갈된 권역만 나무가 사라지고 지형이 평탄해지며 해당 숲 안의 지정 주거 부지가 건설 후보에 들어간다. 아직 남아 있는 숲 안에는 둥지를 건설하지 않는다.
- 지도 전체에 개발용 나무288개(권역32개)를 표시한다. 나무의 지면 높이·제재소·수레는 해당 권역의 지형을 따른다. 이 숫자는 자원의 실제 단위나 최종 아트 개수를 뜻하지 않는다.
- ‘권역별 숲과 작업장’에 숲 잔량·평탄화 여부·배치를 표시하고, ‘숲 권역9곳 / 확보한 부지’로 확장 상황을 요약한다. ‘벌목 현장 보기’는 선택한 권역으로 이동하고, 다른 권역의 생산은 계속된다.

저장은v11이다. v10 원본을 읽을 때 기존 서쪽 숲·계약·재고·배치·진행을 유지하고 새8개 권역만 초기화한다. v11은 `dynosty.timber.saves.v11`에 별도 저장하며 v10 원본은 덮어쓰지 않는다. 권역 중복/누락, 다른 권역의 건설 좌표, 동일 운반자의 중복 배정, 권역별 자원 보존과 전체 공동 재고를 검사한다.

## 복홀 구릉·제재소 개편 (이전 구현, v11 분산 숲으로 확장)

C1 후속 설정: 복홀은 수백 마리와 작업장·거주지가 밀집해 들어갈 넓은 구릉지다. 숲 근처에 제재소를 짓고 직원 수만 정한다. 개별 주민에게 나무를 베라고 지시하지 않는다. 제재소에서 근무한 인원·시간만큼 주변 숲의 자원이 감소하고, 고갈되면 나무가 사라진 평지로 남는다.

- 개발 지도는256×256 좌표, 이동·건설 좌표 한계는±124다. 구릉 위의 건물 기초를 평탄하게 만들고 주민·나무·제재소·수레는 지형 높이를 따른다. 이 크기는 기획 의도를 검증하는 개발 수치이며 현실 지리 축척이 아니다.
- 주거 확장 부지는18곳에서100곳으로 늘렸다. 초기6둥지·60명은 유지하며 인구는 기존 합류 이벤트로만 늘어난다. 600명·주거지100곳의 배정·저장·표시 데이터 검사를 통과했다. 실제600명·100건물이 움직이는 장시간 성능은 별도 검증이 필요하다.
- ‘복홀 전체 보기’로 지도 전체를, ‘벌목 현장 보기’로 제재소를, ‘마을 보기’로 생활 구역을 본다. 오른쪽 드래그로 지도 이동, 왼쪽 드래그로 회전, 휠로 확대/축소한다.
- 제재소는 현재 지정 숲의 공급 반경26 안인 고정 부지1곳이다. 직원은 제재소 바닥 안의 근무 지점으로 출근한다. 기존08~18시 근무·식당 이용·귀가 규칙을 유지한다. 별도의 나무 베기 작업·선택·명령은 만들지 않았다.
- 숲의 잔량에 따라64개의 개발용 나무 표시가 줄어든다. 잔량0이면 해당 숲 구역을 평탄화한다. 다른 구릉은 유지하며, 평탄화는 저장된 잔량에서 재구성하므로 불러오기 후에도 유지된다. 목재를 운반하기 전 고갈됐더라도 이미 채취한 현장·수레 물량은 사라지지 않는다.
- 숲 안의 지정 주거 부지는 숲이 남아 있을 때 제외하고 고갈 후에는 건설할 수 있다. 고갈됐다는 이유로 건물을 자동 건설하거나 제재소 인원을 임의로 해제하지 않는다.
- 저장 형식 필드를 바꾸지 않아 `dynosty.timber.saves.v10` 진행을 그대로 읽는다. 기존 숲 잔량·재고·배치·입주를 보존하고, 이전 직원은 새 제재소 근무 지점으로 이동한 뒤 생산을 재개한다.

검증: 전체 검사198개(25파일), 조달·생활 브라우저16개와 카메라 브라우저1개 통과. 커밋·푸시·PR·병합 없음. 실제 수백 명의 성능, 자유 건물 배치와 길 연결 판정, 여러 제재소/숲의 중첩 채취·재생, 정식 지형 아트와 생산 밸런스는 후속 범위다.

## 벌목소·저장소·자동 운반 v10 (이전 구현, 위 구릉·제재소 개편 우선)

작업 브랜치: `feat/logging-storage-production-20261117`. 이전 식당·배급·거주지 작업을 이어받았다. 커밋·푸시·PR은 별도 승인 대상이다.

1. ‘숲가 벌목소 건설 · 목재20’을 지시한다. 숲 옆 지정 부지에 가까운 건강한 유휴 주민이 이동·건설한다.
2. ‘목재 저장소 건설 · 목재20’을 지시한다. 동시에 한 공사만 진행하며 기존 작업자·운반 인력을 빼앗지 않는다.
3. ‘벌목소 작업 인원’0~4명을 정한다. 자동 배치된 주민이08~18시 실제 근무지에 도착해야 생산한다. 근무가 끝나면 기존 식사·귀가 규칙을 따른다. 식당 직원과 생산·운반 인력은 겸직하지 않는다.
4. 목재는 숲→현장 적재→수레→저장소 순서로 옮긴다. 운반할 목재와 저장소가 있고 영업시간이면 유휴 주민1명이 자동 운반한다. 이미 출발한 운반은 퇴근 시각에도 안전하게 마친다. 출근 인원·이동·건설 중에는 생산하지 않는다.
5. 수레를 내려놓고 하역해야 공동 재고가 증가한다. 이후 손잡이로 돌아가 빈 수레를 벌목소에 복귀·정리하고 주민은 다음 생활 행동으로 돌아간다. 계약 수레와 별개로 작동한다.
6. ‘벌목 현장 보기’와 ‘마을 보기’는 카메라를 이동한다. 숲·기와지붕 작업장·목재 저장소·현장 더미·운반 수레가 상태에 따라 표시된다. 최종 아트가 아닌 개발용 모델이다.

개발용 시험 수치이며 마스터의 확정 밸런스로 보지 않는다: 시설별 건설 목재20·공사8분(이동 제외), 최대4명, 인당 실제 근무10분당 목재1, 숲120, 현장 적재20, 수레 최대5, 내려놓기2분·하역3분·빈 수레 정리2분(이동 제외). 현장 가득 참·숲 고갈·미배치·퇴근 시 생산이 멈춘다. 저장소가 없으면 현장에만 쌓이고 공동 재고로 정산하지 않는다.

저장에는 숲 잔량·적재량·운반 물량·진행·누적 입고·배치·수레 좌표를 함께 기록한다. 숲+적재+수레+누적 입고=120과 공동 목재 장부를 검사해 중복 입고·좌표 위조·유령 인력을 거부한다. 운반 인력이 아프거나 사망하면 유휴 주민이 실제 수레 위치로 와서 교대하며, 인력이 없으면 짐을 보존하고 대기한다. 저장 키는 `dynosty.timber.saves.v10`, v9 원본은 유지하며 자동 변환하지 않는다.

아직 남은 범위: 자유 배치·길 연결 판정, 다른 숲 탐색·재생, 다중 생산시설·다중 수레, 시설별 저장 용량·화재·파괴, 정식 생산 밸런스·도구 소모·난방 생산성. 기존 계약·보수·식당·거주지의 상태 처리와 공동 재고를 재사용한다. 서버 DB 동기화나 전체 캠페인 구현을 의미하지 않는다.

## 식당 인력·종별 배급·실제 거주지 v9 (이전 구현, v10에도 유지)

식당은 건설만으로 운영하지 않는다. 플레이어가 운영 인원0~2명을 정하면 가까운 건강한 유휴 주민을 자동 배치한다. 작업장 배치·기존 임무·식사 중인 주민을 빼앗지 않는다. 직원이 실제 근무지에 도착해야 배급을 시작한다. 현재 시각을 경과 시간과 함께 표시해 영업시간과 비교할 수 있다. 직원은06~22시 자기 식당에서 식사하고 식사 중에는 잠시 배급 인력에서 제외된다. 인원을 줄이면 배치를 해제하고, 질병·사망으로 자리가 비면 유휴 인력을 다시 배치한다.

## 개별 허기·식당 운영·전체 주민 명부 v8 (현재 로컬 구현)

현재 기준은 **검사 입력이나 공통 식사 시각 없이 주민마다 허기가 쌓이고, 근무·지시 업무 중이 아닐 때 영업 중인 식당을 이용하는 것**이다. ‘식사 필요 검사’와 건물 손상을 만드는 개발 버튼을 제거했다. 마을 생활 장면에 진입하면 계약 전에도 시간이 진행된다. 명시적 정지·불러오기·탭 비활성 정지는 유지한다. 새 게임 시각은07:00이며 이전 저장의 시각은 바꾸지 않는다.

식당은 처음부터 존재한다고 가정하지 않는다. 허기진 주민은 식당이 없으면 ‘지휘관님, 배가 고파요. 식당을 지어 주세요!’라고 요구하고, 닫혔거나 식성이 맞는 먹이가 부족하면 그 이유를 알린다. 요구는 주민 위 주황 표식과 지휘 화면에 표시한다. 식당 건설 명령은 가까운 유휴 인력을 예약하며 이동·작업·완료·복귀가 이어진다. 현재 건설 목재20·작업8분·좌석4개는 개발 체험 값이다.

식당06:00–22:00, 작업장08:00–18:00으로 식당이 먼저 열고 늦게 닫히게 했다. 각 주민의 허기가 기준에 도달하면 자동으로 움직이며 별도 집단 식사 시각은 없다. 현재 허기는 분당1, 식사 시작 기준360, 식사 동작5분인 임시 수치다. 시작 허기는 식별값과 명부 순서로 서로 다르게 정한다. 식당 입장에서 허기에 해당하는 식량만 공동 재고에서 차감하고, 같은 시간에 분 단위 식량 소비를 다시 적용하지 않는다. 식사를 시작한 뒤 불러와도 중복 차감하지 않는다. 기존 자원 연결 예제의 비례 소비와 현재 생활 장면의 실제 식당 소비는 구분한다.

표시 인력4명 제한을 없앴다. 등록된60명 전원이 각자 위치·허기·생활·건강 상태를 갖고 표시된다. 합류 사건의 종류별 인원은 같은 명부에 추가되며 즉시 생활·업무 배정 대상이 된다. 식성에 따른 인구·소비·식사 규칙은 동일하다. 같은 사건을 재수신해도 중복 등록하지 않는다. 사망자는 명부에 이력을 남기고 표시·식사·노동에서 제외한다. 누적 사망의 분모가 될 전체 등록 이력을 유지한다. 모델은 아직 전원 트리케라톱스 개발 외형을 공유한다.

C1은 질병·사망 확률의 추가를 보류하고 공통 상태·사건 처리부터 구현하도록 결정했다. `citizen-event`는 `arrival`(종별 인원), `illness`·`recovery`·`death`(주민 식별값 목록)를 받는다. 기존·신규 주민에게 동일하게 적용한다. 담당자가 아프거나 사망하면 유휴 주민이 현장까지 이동해 남은 단계를 인계받으며 이미 입고한 물량을 복제하지 않는다. 인력이 없으면 해당 작업만 대기하고 다른 주민의 허기·생활은 계속된다. 가용 인력이나 신규 인원이 생기면 자동으로 다시 배정한다. 아직 발병·사망 확률식이나 전체 캠페인의 합류 사건 발생 시점은 추가하지 않았다.

둥지는 마우스를 올렸을 때 체력바를 표시한다. 시간·노후화·식량 입고로 건물이 저절로 손상되거나 보수되지 않는다. `building-damage`는 `attack`·`fire` 원인의 사건만 받으며, 보수는 이전처럼 직접 명령한다. 공동 식당의 플랫폼·탁자는 건설 뒤에 표시하는 개발용 외형이다. 건물별 최종 충돌 범위·그래픽과 작업장 전체 생산 UI는 후속 연결 대상이다.

저장 키는 `dynosty.timber.saves.v8`이다. 전체 명부·개별 허기·건강·식당 건설·좌석 예약·교대 중 업무를 함께 검증한다. 식당 건설 종료 시각과 교대 시각을 바꾼 저장은 거부한다. 이전 v7 이하 원본은 보존하고 추정 변환하지 않는다. 공통 마을 저장은 건강·사건 기록이 없는 이전 형식도 읽는다.

검증: 린트·타입·빌드, 단위171개 및 조달 브라우저11개 통과. 자동 식당 요구·건설·식사, 전체60명 표시, 신규 인원·건강 사건과 명부, 근무 중 식사 이탈 금지, 영업시간, 수레 단계, 담당자 사망 뒤 실제 교대, 건설 인력 교대, 중간 저장·변조 거부, 마우스 체력바·직접 보수, 모바일을 포함한다. 전체 DB·미디어 회귀와 캠페인 밸런스는 재검사하지 않았다. 아래 v1~v7은 이전 구현 이력이며 현재 기준은 이 v8이다.

## 주민 생활 동선과 수레 내려놓기 v7 (현재 로컬 구현)

수레가 판자 위에 정차하면 손잡이를2분 동안 내려놓고, 운송 주민이 옆으로 물러난 다음 하역한다. 복귀 중에 수레를 회전시키지 않는다. 운송뿐 아니라 건조·보수를 마친 모든 체험 인력에게 같은 생활 동선을 적용한다.

업무 종료 후 **예약된 다음 지시 → 식사 필요 시 공동 식당 → 집 → 집이 없으면 따뜻한 대기 지점** 순서로 목적지를 정한다. 현재 업무나 작업장 배치를 생활 동선이 빼앗지 않는다. 후속 업무 명령은 주민을 지정하지 않고 장소와 업무 식별값으로 접수하며 도달 가능한 가까운 인력을 자동 선택한다. 복귀 중 명령이면 현재 위치에서 경로를 다시 계산한다. 후속 생산 업무 자체와 작업장 인원수 UI 전체가 구현된 것은 아니며, 이번에는 이동과 인계까지의 공통 경계를 제공한다.

공동 식당은 장면의 탁자로 표시한다. 주민별 식사 위치를 분리하고, 맞는 식량이 없으면 식당에서 기다린다. 식사 종료 후 다시 집·대기 지점으로 돌아간다. 식량은 기존 식성별 분 단위 정산에서만 소비하며, 식당 방문으로 추가 차감하지 않는다. **식사 간격6시간·식사 동작5분은 동선 확인용 임시값**이다. 개별 포만도·이동 시간에 따른 기아 피해나 온도별 휴식 효율은 아직 구현하지 않았다. 개발 도구의 **식사 필요 검사**로 기다림 없이 동선을 확인할 수 있다.

기존 인구 데이터는 트리케라톱스20명(풀), 벨로키랍토르20명(고기), 스피노사우루스20명(어류)다. 식성별로 해당 식량만 소비한다. 모델이 하나여서 모두 트리케라톱스로 보였던 점을 구분하도록 인구 구성을 재고 아래 표시했다. 세 종의 최종 모델은 이번에 제작하지 않았다.

저장 키는 `dynosty.timber.saves.v7`이다. 수레 정차·손잡이 이탈과 주민별 다음 지시·식사 시각·생활 상태를 검증한다. 이전 v6 이하 키는 보존하며 새 체험에서 시작한다. 기존 버전 기록을 새 행동 시간으로 추정 변환하지 않는다.

검증: 린트·타입·빌드, 단위155개, 조달 브라우저10개 통과. 식성 한 종류일 때 해당 식량만 소비, 수레 정차·내려놓기·이탈, 건조와 보수 후 귀가, 복귀 중 후속 지시 재경로, 식량 부족 대기, 식사 중 저장·복원과 이중 소비 방지를 포함한다. 아래 v6은 이전 동작 기록이며 변경된 부분은 v7을 우선한다.

## 자동 업무와 공동 재고 v6 (현재 로컬 구현)

C1의 현재 기준은 **계약 → 유휴 주민 자동 배정 → 수레 운송 → 야적장 하역 → 전량 검수 → 주민 복귀 → 공동 재고 정산 → 다음 임무**다. 정상 화면에서 주민 선택과 출발·하역·검수·수령·건물별 배분 버튼을 제거했다. 시간 정지·배속·저장은 유지하고 단계 건너뛰기는 개발 도구에만 남겼다.

수레의 도착 기준은 야적장 판자의 중심이다. 운송 중 주민 위치와 방향은 짐을 실은 수레의 손잡이를 기준으로 맞춘다. 하역하면서 수레의 짐이 줄고 완료하면 빈 수레가 남는다. 주민은 건물과 야적장을 우회해 복귀한다. A의 젖은 목재4는 유휴 인력2명이 자동 건조·재검사한다. 인력이 부족하면 대기하며 기존 작업장 인력을 빼앗지 않는다.

조달 상태가 마을의 실제 공동 재고와 시간을 함께 보관한다. 계약 비용은 공동 철재에서, 합격품은 공동 목재에 한 번만 반영한다. 별도의 둥지 배분은 없다. 검수 대기·격리품은 가용 재고에 포함하지 않는다. 진행 중 기존 식량 소비 규칙도 계속 적용한다. 기본 재고 기준으로 목재120→140, 철재40→A36/B34다. 개발 도구로 마을 현황에 돌아가도 정산한 재고를 전달한다.

둥지 목재 배분을 난방이나 자동 보수로 해석하지 않는다. 정상 건물은 그대로 두며, 손상 건물은 명시적인 **건물 보수 명령**과 공동 목재20, 도달 가능한 유휴 주민이 있어야 보수한다. 가까운 주민이 이동해 작업을 마쳤을 때 재료를 소비한다. 이번 변경에서 연료 소비·화재·자동 노후화 규칙은 추가하지 않았다.

조달 완료 후 최신 마스터의 **P01 복홀 호구와 먹이 장부**를 자동 표시한다. ‘구휼 장부 우선/호패 대조 우선’ 결정을 저장한다. 이후 전체 시나리오의 사건·정책 효과와 60명 전체 작업장 자동 배정은 아직 연결하지 않았다. 화면의 실제 작업 인력은4명인 개발 체험이며 최종 한국식 건물·손잡이를 쥐는 세부 동작도 후속 대상이다.

저장 키는 `dynosty.timber.saves.v6`이며 공동 재고·계약·부분 하역·주민 예약·장부 결정을 함께 검증한다. 이전 저장 키는 보존하고 추정 변환하지 않는다. 불러오기와 탭 비활성은 정지 상태로 복원한다.

검증(2026-11-17): 린트·타입·빌드, 단위142개 및 조달 브라우저8개 통과. 계약 이후 실제 시간만으로 A 자동 완주, B 정산, 중간 저장 복원·중복 입고 방지, 나가기 후 공동 재고, 직접 보수, 손상 저장 보존, 비활성 정지, 모바일 조작을 포함한다. 실제 화면에서도 B 계약 후 추가 작업 명령 없이 빈 수레·주민 복귀·공동 목재140·철재34·P01 표시를 확인했다. 전체 DB·미디어 회귀와 캠페인 밸런스는 이번에 재검사하지 않았다. 커밋·푸시·PR 생성은 하지 않았다.

## 직접 보수 명령 v5 (현재 로컬 구현)

C1 지시: 목재 배분은 보수 명령이 아니다. 정상 건물은 보수하지 않는다. 손상 건물이라도 사용자가 직접 명령했을 때만 시작한다. 작업장에 배치되었거나 다른 업무를 수행하는 주민은 제외하고, 도달 가능한 유휴 주민 중 이동 경로가 가장 짧은 주민을 선택한다.

새 체험의 집은 내구도100인 정상 건물이다. 목재20을 확보·배분해도 주민은 보수에 들어가지 않는다. 손상도와 재료를 확인하고 **건물 보수 명령**을 눌러야 이동·작업·자재 소비가 이어진다. 파괴된 내구도0 건물은 보수 대신 재건이 필요하다고 표시한다. 보수 완료 시 내구도를100으로 회복하고 예약 인력을 해제한다.

이 동작을 검증하려면 **개발 도구 → 건물 손상 검사 (-25)**를 사용한다. 이는 수동 QA 명령이며 자동 노후화·화재 사건을 구현한 것이 아니다.100 내구도·25 검사 손상·20 목재·8분 보수는 체험의 개발 기준이며 본편 비용/피해 확정값이 아니다.
